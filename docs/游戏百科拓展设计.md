# 神谕百科(Oracle of Games) —— 拓展设计文档

> 基于现有 `ai-chat` 项目(Spring Boot 3.4 + Spring AI 1.0 + Vue3)拓展,产品名:神谕百科。  
> 核心功能:**智能问答** + **游戏知识库**。  
> 硬件约束:服务器 2核2G、内存 <1G;**仅 MySQL,无 Postgres / 无 Ollama**。



---

## 1. 需求概述

| 模块       | 功能                      | 说明            |
| -------- | ----------------------- | ------------- |
| **智能问答** | 玩家提问,基于知识库资料回答,流式输出     | 复用现有 SSE 聊天链路 |
| **知识库**  | 游戏资料上传 / 浏览 / 检索测试 / 删除 | 新增管理页         |
| 引用溯源     | 回答中标注引用的知识条目            | RAG 的可信度关键    |
| 游戏维度     | 按游戏隔离知识,先选游戏再问答         | 检索性能与准确性核心优化  |

**内容范围**:市面上热门游戏的基础信息(发行商/类型/平台/发售日)、玩法机制、攻略、角色/武器/物品图鉴、版本更新、赛事活动等。

## 2. 系统架构

```
┌────────────────────────── 前端 Vue3 ──────────────────────────┐
│  智能问答页(聊天 + 引用来源)   知识库管理页(上传/浏览/检索)      │
│  (复用:Markdown 渲染 / SSE 流式 / 停止生成 / 复制 / 语音)      │
└────────────────────────────┬─────────────────────────────────┘
                             │ HTTP / SSE
┌────────────────── 后端 Spring Boot(现有项目拓展) ─────────────┐
│  问答服务:检索 TopK → 拼接 SystemMessage → 流式回答            │
│  知识库服务:文档解析 → 分块 → 嵌入 → 入库                    │
│  新增:RagService / ChunkRepository / KnowledgeController      │
└──────────┬──────────────────┬──────────────────┬──────────────┘
           │                  │                  │
   ┌───────▼───────┐  ┌───────▼────────┐  ┌─────▼──────────┐
   │ MySQL(现有)   │  │ ONNX 本地嵌入  │  │ DeepSeek LLM   │
   │ game/article  │  │ bge-small-zh   │  │ OpenAI 兼容    │
   │ chunk(含向量) │  │ 纯 Java        │  │ 流式(现有)     │
   └───────────────┘  └────────────────┘  └────────────────┘
```

**关键决策**:不引入 Postgres / Ollama,全部用现有环境 + Java 生态解决:

- 向量存储 → **MySQL 存向量(JSON)+ Spring AI `SimpleVectorStore` 内存检索**(免装 Postgres,余弦计算交给框架,应用层零手写);
- 本地嵌入 → **ONNX 格式 bge-small-zh + onnxruntime**(纯 Java,免装 Ollama)。

> 选型结论:社区版 MySQL 9.x 的 `DISTANCE()` 函数仅限 Oracle HeatWave,升到 9.x 也无法在 SQL 内算相似度;  
> 换 Postgres + pgvector 在 2G 服务器上要新增一个常驻数据库服务(内存/运维/迁移成本高),  
> 而框架自带 `SimpleVectorStore` 已提供同样的"一行检索"体验 —— 故维持"MySQL 存 + SimpleVectorStore 检索"。

## 3. 核心流程

### 3.1 知识入库(离线/管理操作)

```
上传文档(按游戏归类)
  → 解析:PDF/Word/TXT → 纯文本(Spring AI document-reader)
  → 分块:TokenTextSplitter(500 token / 重叠 50)
  → 嵌入:本地 bge-small-zh(512 维)→ float[]
  → 入库:chunk 表(game_id, article_id, content, embedding, meta)
```

### 3.2 智能问答(在线)

```
用户选择游戏(如"原神")→ 提问
  → 问题嵌入(同一模型)
  → 检索:SimpleVectorStore.similaritySearch(query, topK=3~5)
        (启动/按游戏懒加载 chunk 进内存,余弦由框架内部完成;阈值 0.5)
  → 拼接:检索片段作为 SystemMessage("以下为游戏资料,请基于资料回答...")
  → 流式回答(复用现有 SSE 链路)+ 返回引用条目列表
```

> 神谕百科场景的天然优势:**先选游戏再提问**,检索可以在 game_id 维度预过滤,  
> 既提升准确率又大幅缩小计算量(单游戏仅几百~几千块,内存检索 <100ms)。

## 4. 数据模型(MySQL)

> 所有表统一归属独立库 **`ai_chat`**,DDL 均带 `ai_chat.` 前缀,与服务器上其他项目表隔离。
> 首次部署建库(账号需建库权限;schema.sql 顶部自动执行):

```sql
CREATE DATABASE IF NOT EXISTS ai_chat CHARACTER SET utf8mb4;
```

```sql
-- 游戏表
CREATE TABLE ai_chat.game (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(100) NOT NULL,          -- 游戏名,如"原神"
  category    VARCHAR(50),                    -- 类型:MOBA/FPS/开放世界...
  platform    VARCHAR(100),                   -- 平台:PC/PS5/移动端...
  publisher   VARCHAR(100),
  release_date DATE,
  summary     TEXT,                           -- 一句话简介
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 百科条目表(结构化资料:攻略/角色/武器/版本更新...)
CREATE TABLE ai_chat.article (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  game_id     BIGINT NOT NULL,
  title       VARCHAR(200) NOT NULL,          -- 条目标题
  type        VARCHAR(30),                    -- 攻略 / 角色 / 武器 / 机制 / 新闻
  source      VARCHAR(200),                   -- 来源(官方公告/社区/wiki)
  content     MEDIUMTEXT,                     -- 正文
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_game (game_id)
);

-- 分块表(向量 + 原文,检索核心)
CREATE TABLE ai_chat.chunk (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  game_id     BIGINT NOT NULL,                -- 冗余 game_id 便于过滤
  article_id  BIGINT NOT NULL,
  content     TEXT NOT NULL,                  -- 分块文本
  embedding   JSON,                           -- 512 维 float 数组
  meta        VARCHAR(255),                   -- 章节/页码等定位信息
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_game (game_id)
);

-- 会话表(智能问答多会话,新增于"多会话管理"功能)
CREATE TABLE ai_chat.conversation (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  title       VARCHAR(200) NOT NULL,          -- 会话标题(默认取首条提问前 20 字)
  game_id     BIGINT,                         -- 会话绑定的游戏(空=通用)
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 会话消息表(问答落库,重启/换端不丢)
CREATE TABLE ai_chat.chat_message (
  id              BIGINT PRIMARY KEY AUTO_INCREMENT,
  conversation_id BIGINT NOT NULL,
  role            VARCHAR(20) NOT NULL,       -- user / assistant
  content         MEDIUMTEXT NOT NULL,
  references_json TEXT,                       -- 参考来源(JSON 数组,仅 assistant)
  created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_msg_conv (conversation_id)
);
```

> 完整可执行 DDL 见 `backend/src/main/resources/schema.sql`(幂等 `CREATE TABLE IF NOT EXISTS`,MySQL/H2 通用,应用启动自动执行)。

**为什么 MySQL 存 JSON 向量可行**:

- 512 维 float 数组 JSON 约 3~4KB/条;5 万条 ≈ 200MB 存储,MySQL 无压力;
- 检索时按 game_id 过滤后(单游戏通常几百~几千块),**在应用层加载这些向量算余弦相似度**:  
  5000 条 × 512 维 ≈ 10MB 内存,一次检索纯计算 <100ms,2G 服务器完全扛得住;
- 平滑升级:未来规模大了,可无痛迁移到 PGVector / Milvus(查询接口不变,只换实现)。

## 5. 技术选型调整说明

| 原计划                          | 调整后                                     | 理由                                                                                              |
| ---------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| PGVector(需装 Postgres)        | **MySQL JSON + SimpleVectorStore 内存检索** | 服务器只有 MySQL;换 PG 需新增常驻数据库服务(2G 内存吃紧);Spring AI `SimpleVectorStore` 已内置余弦检索,框架封装后与 PG 体验一致       |
| Ollama(需装容器)                 | **ONNX + onnxruntime(纯 Java)**          | 不引入容器/模型服务;bge-small-zh-v1.5 ONNX 文件约 50MB,加载后内存约 200MB;Spring AI 有 `spring-ai-model-onnx` 直接支持 |
| RetrievalAugmentationAdvisor | **保留**,但先手动拼接                           | 第一步手动拼接(检索→拼 SystemMessage)便于理解与调优;稳定后再用 Advisor 简化                                             |

**嵌入模型备选**:

- 首选:**本地 bge-small-zh-v1.5(ONNX,int8 量化)** —— 免费、离线、中文效果好;
- 备选(最简起步):**通义 text-embedding-v3 API** —— 零本地资源,但要网络 + 按量计费;
- 注意:入库与查询必须用**同一嵌入模型**,否则向量无法比较。

### 5.1 bge-small-zh-v1.5 服务器部署步骤(ONNX 方案,纯 Java)

> 不需要装 Ollama / Python / 任何容器。应用用 `onnxruntime`(纯 Java 依赖)直接加载模型文件。
> **实际只加载 2 个文件**:`model.onnx`(~90MB)+ `tokenizer.json`(~500KB,在仓库根目录,不在 onnx/ 下)。`config.json` 不需要。

**① 下载模型文件(2 个,合计约 90MB)**

```bash
# 在服务器建目录
mkdir -p /opt/ai-chat/models/bge-small-zh-v1.5 && cd /opt/ai-chat/models/bge-small-zh-v1.5

# 国内推荐 hf-mirror 镜像(快);也可本地下载后 scp 上传
wget https://hf-mirror.com/Xenova/bge-small-zh-v1.5/resolve/main/onnx/model.onnx
wget https://hf-mirror.com/Xenova/bge-small-zh-v1.5/resolve/main/tokenizer.json

# 校验大小(断流时用 wget -c 续传)
ls -lh
# 预期:model.onnx ≈ 90MB;tokenizer.json ≈ 500KB
```

> 备选镜像:ModelScope 搜 `bge-small-zh-v1.5` 下载同名文件;下载后校验 `model.onnx` 大小约 90MB。  
> 文件路径以对应仓库实际目录为准(本实现:`model.onnx` 在 `onnx/` 下,`tokenizer.json` 在根目录)。

**② 实际集成方式(已实施)**

> Spring AI 1.0 GA 无 ONNX 官方模块(仅 M6),项目改为**手动集成**:
> `onnxruntime 1.16.3`(模型推理)+ `ai.djl.huggingface:tokenizers 0.20.0`(中文分词),
> 类 `config/LocalBgeEmbeddingModel`,并手动实现 bge 检索前缀(`为这个句子生成表示以用于检索相关文章:`)  
> + CLS pooling + L2 归一化,与官方推理逻辑对齐。依赖见 `backend/pom.xml`,无需额外配置。

**③ application.yml 配置(已实施,路径可用环境变量覆盖)**

```yaml
ai-chat:
  onnx:
    model-path: ${AI_MODEL_PATH:/opt/ai-chat/models/bge-small-zh-v1.5/model.onnx}
    tokenizer-path: ${AI_TOKENIZER_PATH:/opt/ai-chat/models/bge-small-zh-v1.5/tokenizer.json}
```

**④ 使用(已实施)**

```java
// LocalBgeEmbeddingModel 是 @Component,注入即用
private final LocalBgeEmbeddingModel embeddingModel;
float[] vec = embeddingModel.embed("原神 甘雨 配队");   // 512 维
```

**⑤ 内存与验证**

- 加载后常驻内存约 **150~250MB**(onnxruntime + 模型);部署前 `free -m` 核算:  
  JVM(-Xmx192m)+ MySQL + ONNX(≈200MB),若紧张可将 ONNX 与主应用分进程部署;
- 验证:启动日志出现 ONNX 模型加载成功;调一个测试接口返回 512 维向量;
- 注意:bge-small-zh-v1.5 输出 **512 维**,chunk 表 `embedding` 字段维度需一致(入库/查询同模型)。

**⑥ 备选方案(更省事但联网+计费)**:通义 `text-embedding-v3`  
`AI_BASE_URL` 配 DashScope 兼容地址 + 单独一个 embedding API key,`spring.ai.openai.embedding.*` 配置即可,零本地资源——建议 P0 用这个跑通,再切本地 ONNX。

## 7. 知识库内容规划

| 资料类型       | 内容               | 来源建议       | 更新频率  |
| ---------- | ---------------- | ---------- | ----- |
| 游戏基础信息     | 类型/平台/发行商/发售日/简介 | 官方/维基      | 低频    |
| 玩法机制       | 系统说明、数值公式、流派     | 官方公告、社区精华帖 | 版本更新时 |
| 攻略         | 主线/副本/BOSS/速通    | 社区攻略、wiki  | 持续    |
| 角色/武器/物品图鉴 | 属性、获取方式、评价       | wiki、官方    | 版本更新时 |
| 版本更新       | 补丁说明、活动          | 官方公告       | 高频    |

**整理规范**:每篇资料建议结构化(标题 + 章节),便于分块后语义完整;  
标题即摘要(如"原神-3.0版本-须弥新增角色"),检索命中率更高。

## 8. 分阶段实施

| 阶段         | 内容                                    | 工作量   | 交付       |
| ---------- | ------------------------------------- | ----- | -------- |

### 部署配合清单(3 件事)

1. **MySQL 连接信息**:新建库 `ai_chat`(或自定),把 `application.yml` 的  
   `spring.datasource.url/username/password` 改成你的实际值(启动自动建表,无需手动执行 SQL);
2. **模型文件上传服务器**(2 个文件,约 90MB):
   ```bash
   mkdir -p /opt/ai-chat/models/bge-small-zh-v1.5 && cd /opt/ai-chat/models/bge-small-zh-v1.5
   wget https://hf-mirror.com/Xenova/bge-small-zh-v1.5/resolve/main/onnx/model.onnx
   wget https://hf-mirror.com/Xenova/bge-small-zh-v1.5/resolve/main/tokenizer.json
   # 校验:model.onnx ≈ 90MB;tokenizer.json ≈ 500KB(断流用 wget -c 续传)
   # 若换目录,同步改 application.yml 的 ai-chat.onnx.* 或用环境变量 AI_MODEL_PATH/AI_TOKENIZER_PATH
   ```
3. **启动**(推荐 compose,已配 `mem_limit: 400m` 和模型目录挂载):
   ```bash
   docker compose up -d --build
   # 关键:docker-compose.yml 已配置 volumes 挂载 /opt/ai-chat/models → 容器同路径
   # 模型文件必须放在宿主机 /opt/ai-chat/models,否则容器内加载失败
   ```

> 注意:jar 约 167MB(onnxruntime 全平台 native + jsoup + POI/PDFBox),首次 scp 上传会慢一些,属正常。

## 9. 风险与注意

1. **内存预算**(2G 服务器):应用 JVM(-Xmx192m)+ MySQL + ONNX 嵌入(~200MB)  
   需提前 `free -m` 核算,必要时嵌入服务与应用分进程部署;
2. **嵌入模型一致性**:换模型必须全量重新入库,否则检索失效;
3. **文档格式**:PDF 解析依赖字体/扫描件质量,扫描件需 OCR(可后置);
4. **内容版权**:资料整理优先用**官方公告/自撰攻略**,搬运社区内容注意版权与来源标注;
5. **检索质量**:分块大小、TopK、阈值需用真实问题回归测试,按游戏预过滤是首要优化项。
